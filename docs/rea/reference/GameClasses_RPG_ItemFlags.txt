FINDING (observed, high confidence)
===================================
The registry property `*flags` on an RPG item is parsed by the
CRPG_Object_Item property registrar

    FUN_100dfbd0   GameClasses_Win32_x86.dll   0x100dfbd0 .. 0x100e0b31

which references the property name "FLAGS" at 0x100e0568 alongside
MODEL / WEAPONGROUP / ATTACHPOINT / MUZZLEATTACHPOINT / ITEMTYPE / SKILL /
MAXITEMS / ANIM_* / SOUND_* / ICONSURFACE / PICKUPMSG / ... (item props).

   (`in_ECX` is the item object being constructed — the same object the other

FUN_100095a0 -> FUN_10009160 is the generic token-string -> bitmask translator
(the same helper family is reused for every name-set property, e.g. SKILL with
&PTR_s_unarmed_101f72fc). Core loop (Ghidra pseudocode):

A token beginning with '-' or '0'..'9' is parsed numerically and OR'd raw
instead (so `*flags 0x13` and `*flags noviewmodel+...` both work).

=> the bit of a flag = 1 << (0-based index of its name in the table).

READER LEAD (observation — consumer NOT yet proven)
==================================================
A masked scan for `test dword [reg+0x14c], 2` (F7 /8x … 02 00 00 00) matched
**nothing** in the module. The byte form matched once:

    0x10037111   F6 80 4C 01 00 00 02     test byte ptr [eax + 0x14c], 2

inside  FUN_10037020  (0x10037020 .. 0x100372bc; sole caller FUN_10040aa0).
That function queries an entity by class name (fallback string
"info_player_start" @0x101bc260), selects the first entity whose `[+0x14c]`
bit1 is set (else random), copies a 4x4 from `entity + 0xa8`, applies
camera-space offsets from `this + 0x4e4 / +0x524`, and returns the low 16 bits
of `[+0x14c]` through an out-parameter. The bits it tests (0x1, 0x2, 0x20 =
wallcollision / noviewmodel / aiming) line up with this table, but the
surrounding role is player-start / camera-entity selection, so this is **not
proven** to be the viewmodel draw gate. Treat it as the only direct `& 2`
reader of `+0x14c` found so far (F6 forms for modrm 0x81..0x87 were not
exhaustively scanned).
