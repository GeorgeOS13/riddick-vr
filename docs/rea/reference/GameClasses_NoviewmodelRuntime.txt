Reading: `+0x14c` is the RPG-item `*flags` bitfield (ADR-0435), so the object is
an RPG item/weapon instance. `+0x212` is a saturating (<0xfe) per-frame counter;
`+0x210`/`+0x211` are byte thresholds; `+0x204` is a short gate. The bit is set
after `+0x210` frames and cleared after `+0x211` frames when `+0x204 != 0` — a
hysteresis/state machine that notifies `FUN_100dcb90(..., 0x1056, ...)` on every
transition (0x1056 is very likely an anim property/event id). `0x100dcb90` and
`0x100e6450` are not decompiled here.

INFERENCE (not proven)
======================
- `noviewmodel` behaves as an engine *output* of an item state machine (weapon
  idle/raise-lower style hysteresis), not as a simple boolean input to a draw
  gate. Since no code path masks bit 1 to make a draw decision, forcing the bit
  from the hook is not expected to suppress the first-person viewmodel.
- A *copy-based* consumer (the flags snapshotted into another structure, then
  compared) cannot be excluded by a mask scan, so this is not a proof that the
  bit is inert — only that it has no direct mask reader.
- Class identity of the FUN_100e6aa0 object is inferred from layout (it carries
  the RPG-item `*flags` at +0x14c); the MSVC RTTI COL chain is not recoverable
  from the file (no COL references the type descriptors), so the exact class
  (`CRPG_Object_Item` vs `CRPG_Object_Weapon` vs a client-data type) is not
  claimed.
